# Disposable staging2 authorization qualification

This procedure supplies the live bindings for the already approved selected
authorization cases. It does not change the cases or application permissions.
The [verification catalog and binding contract](authorization-verification.md)
own the 29 cases, expected policies, positive baselines and exact value aliases.
The four-account/two-teacher scope was explicitly approved on 2026-11-11.
Executor preparation and verification must finish before live writes; preparing
this procedure created no account or teacher grant.

## Access decision and isolation

The retained Windows credential set has administrator, observer and two learner
PSCredential files, but no teacher bindings. Absence of a credential file does
not prove that an account is absent. Do not reset or repurpose an existing
teacher account, guess credentials, reuse production credentials or reread the
recovery backup to make this test work.

The proposed bounded permission is to create exactly four disposable ordinary
staging2 accounts: learnerA/B and teacherA/B. Only teacherA/B receive the existing
`teacher` role. None receives `admin`. The existing staging2 administrator is
used only for the already selected admin baselines and scoped fixture ownership.
All four new accounts and their teacher assignments are removed after the test.
They can appear in the staging2 admin user list during the qualification window.

These disposable learner/teacher fixtures are part of the approved staging2
synthetic qualification. Do not ask again for this same scope. The standing
exception for new security-sensitive access must not turn ordinary approved
fixture work into another per-batch permission boundary. New persistent admin
identities, existing-account resets and production operations remain excluded.
No AWS access, production/original-staging access, new provider account, paid
request, new system dependency, public management port or permanent service is
part of this procedure.

## Prepare before any account write

1. Bind the approved staging2 hostname, current candidate image/source and
   catalog to the retained build/publication/Meteor evidence. Keep the accepted
   candidate/previous/candidate storage proof; do not repeat it unchanged.
2. Generate one fresh unpredictable fixture namespace and four strong passwords
   in the protected operator process. Bind each exact account ID/username to
   that namespace. Keep credentials only in private process input or root-only
   temporary files; never in command arguments, console output or artifacts.
3. Validate the installed native Accounts password representation, the existing
   teacher-role definition, collection ownership and complete fixture document
   shapes before using them. Use the pinned native password implementation;
   do not invent a hash format or add an application fixture endpoint. Verify
   these paths in the isolated supported environment before live insertion.
4. Prepare the cleanup manifest and failure recovery first. It names only new
   account IDs, their role assignments, exact synthetic progress/history rows
   and a non-functional settings canary. Require unused identifiers and
   insert-only creation. An existing ID/name is a collision, never an account
   password-reset or upsert opportunity.
5. Prepare known synthetic export content through its actual formatter and bind
   its exact bytes/hash. A hash copied from an unchecked live download cannot
   establish correct ownership. Construct the value-only binding subset and
   validate it through `parseAuthorizationBindingsV2` before browser execution.

## Execute the bounded qualification

- The root fixture owner and a separate recovery operator session remain
  available through the operation. Use one exclusive per-environment window,
  bounded child timeouts and cleanup traps. Do not run two fixture owners.
- Create only the four new accounts and two teacher assignments. Never alter
  the existing admin, learner or teacher accounts. Do not modify deployed
  settings, provider secrets, role definitions, learner histories/model state,
  course assignments or TDF content to obtain a pass.
- Seed only the manifest's synthetic progress/history rows and canary. Use the
  accepted V2 report's ID/digest for the admin download baseline. No report
  rewrite or deletion is needed.
- Confirm real password login and exact hydrated actor roles. Failed login,
  an unexpected admin role, a missing canary or an unexpected identity aborts
  the qualification; it cannot become a successful denial.
- Run the source-owned browser adapter. Allowed baselines execute first and
  every selected denial depends on its successful baseline. Only finite
  outcomes, catalog IDs, counts and public proof hashes leave acquisition.
  No mailbox, synthesis, LLM or other provider request is required by these cases.

## Cleanup and acceptance

Remove only the manifest-owned canaries/history/progress records, teacher
assignments and four accounts, with exact ownership predicates. Account removal
invalidates their sessions. Preserve immutable accepted audit reports and normal
application audit-log receipts. Independently verify absence of all owned
accounts/assignments/data and removal of temporary credential files.

On a timeout or SSH observation failure, inspect the same owner/job before any
retry. An untrappable process/host failure can leave fixture access behind; no
automatic account expiry is claimed. Retain its protected cleanup manifest and
recover those exact owned records before starting another fixture job. Do not
add a TTL index or change account storage to conceal that operational boundary.

Acceptance requires all 29 selected cases, their required positive baselines,
successful browser cleanup, unchanged non-fixture records and independent
fixture/access cleanup. Record honest failed attempts. Source/Meteor model tests
or a transport-valid report alone do not close live selected-case acceptance.
